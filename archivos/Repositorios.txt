Graft crea un mapa vivo de tu repositorio para que Claude Code y otros agentes entiendan la arquitectura antes de empezar a trabajar.

→ Genera una ficha en Markdown para cada parte relevante del sistema
→ Guarda resúmenes, dependencias, archivos fuente y relaciones entre componentes

3/ ¿Cómo instalarlo?

Otra vez descubro un proyecto open source rarísimo llamado Repowise, que puede indexar todo tu repositorio de código en un mapa que la IA puede consultar, para que Claude Code deje de revolver como loco por todo el repositorio buscando archivos.

En GitHub tiene 7672 estrellas, el repositorio se creó a finales de marzo, y últimamente casi sacan una versión por semana, de v0.52 a v0.56 todas apiñadas en septiembre y octubre.

Normalmente, cuando le pides a la IA que modifique un trozo de código viejo, primero tiene que hacer un grep por todo el repositorio, leer un montón de archivos irrelevantes, y en la salida todo son «voy a echar un vistazo a este archivo». Lo que hace Repowise es indexar de antemano en tu máquina local la estructura del código, el grafo de llamadas, el historial de Git, las pruebas y la documentación, y luego exponerlo a través de MCP para que herramientas como Claude Code, Codex o Cursor lo consulten; el agente pregunta directamente al índice lo que necesita. El proyecto ha hecho pruebas emparejadas en 43 issues de Django, y para el mismo trabajo la cantidad de salida se reduce un 31.6%.

Lo más práctico es ese sistema de puntuación de salud del código: 53 detectores le dan a cada archivo una puntuación de 1 a 10, y además señalan qué bloques tienen el mayor riesgo si los cambias y cuáles son código muerto. El grafo, los riesgos y el grado de salud son todo cálculos determinísticos, sin una sola llamada a un modelo grande, y no hace falta configurar ninguna API key.

Hacer que la IA entienda tu repositorio es más efectivo que cambiarle por un modelo más grande.

https://github.com/repowise-dev/repowise

ESTO ES UNA PUTA MINA DE ORO

el mejor truco de REA que casi nadie usa todavía.

La idea: REA desarma la app, Jev conserva solo lo que está probado, y un fresco Opus 5.5 reconstruye la función solo a partir de eso.

Nada se copia y ninguna suposición entra en el código, porque el constructor nunca ve el original, solo la spec que Jev aprobó.

Solo conectas REA así:

npx rea-agents setup

aquí está la división:

→ REA lee la función hasta el binario y escribe cada regla en SPEC.md
→ Jev verifica cada regla contra la evidencia de REA y devuelve cualquier cosa no probada
→ una sesión fresca de Opus 5.5 recibe solo SPEC.md y reconstruye la función
→ Haiku 5.5 ejecuta las pruebas contra 3 versiones intencionalmente rotas

Opus solo aparece en tres momentos:

→ reconstruyendo desde la spec aprobada
→ las verificaciones que Jev marca como poco claras
→ aprobando antes de que nada se envíe

REA lee. Jev juzga. Opus reconstruye.

Esa es la regla de sala limpia en una línea: el modelo que vio el original nunca escribe el código, y el modelo que escribe el código nunca ve el original.

el árbol completo
> REA lee la app y escribe SPEC.md con evidencia para cada regla
> Jev aprueba o devuelve cada regla
> Opus 5.5 reconstruye desde el SPEC.md aprobado en una sesión fresca
> Haiku 5.5 ejecuta las pruebas y las 3 versiones rotas
> Jev ruta las verificaciones poco claras de vuelta a Opus
> /goal sigue hasta que todas las 3 versiones rotas fallen

pega el árbol y este prompt en Claude Code ↓

"Configura una reconstrucción de sala limpia alrededor de este árbol:
1. Usa REA para investigar [FEATURE] en [APP]. Escribe cada comportamiento y regla en SPEC.md, cada una con la evidencia que REA encontró.
2. Envía cada regla a Jev. Cualquier regla sin evidencia vuelve a REA.
3. Inicia una sesión fresca con solo SPEC.md. Reconstruye la función en Opus 5.5 sin abrir el original.
4. Escribe pruebas en Haiku 5.5 más 3 versiones intencionalmente rotas. Usa /goal hasta que la reconstrucción pase y todas las 3 versiones rotas fallen.
Muéstrame primero SPEC.md. Nada se construye hasta que yo diga adelante."

↳ https://github.com/morluto/rea

¡Convierte documentos en datos aptos para agentes!

OXR es un modelo de análisis de documentos de código abierto de 1.3 mil millones de parámetros que transforma PDFs e imágenes de documentos en Markdown o JSON estructurados.

En lugar de extraer solo texto, reconoce 13 elementos de documentos diferentes, incluyendo tablas, fórmulas, figuras, bloques de código, notas al pie y estructuras químicas, al mismo tiempo que preserva el orden de lectura y las coordenadas de diseño.

Eso hace que la salida sea mucho más útil para RAG y agentes, donde saber qué dice el texto es solo una parte del problema. También necesitas saber qué es una tabla, dónde pertenece una fórmula, qué pie de figura corresponde a qué figura y cómo se debe leer realmente el documento.

La parte técnica que me pareció interesante es cómo se post-entrenó OXR.

Utiliza un bucle de auto-mejora recursiva donde OXR primero analiza documentos sin etiquetar, luego un VLM general revisa las salidas en busca de errores e incertidumbre.

Las discrepancias en múltiples ejecuciones de OXR ayudan a identificar ejemplos inciertos, esos fallos se agrupan por causa y el VLM genera datos de entrenamiento dirigidos para la siguiente ronda.

Así, en lugar de etiquetar manualmente nuevos datos para cada iteración, los propios fallos de análisis del modelo ayudan a decidir en qué debería entrenarse a continuación.

La arquitectura también es diferente de la tubería de análisis habitual.

El análisis de diseño permanece independiente y modular, mientras que el reconocimiento y el orden de lectura consciente del contenido se ejecutan en paralelo dentro del modelo principal. Eso significa que los equipos pueden reemplazar el modelo de diseño por su propia estructura de documentos sin reemplazar el resto de OXR.

Y los resultados son sólidos para un modelo de 1.3 mil millones de parámetros.

OXR ocupa el #1 en olmOCR-Bench, OmniDocBench y DocParsingBench. En la prueba de velocidad reportada de 100 páginas en una sola RTX PRO 6000, OXR terminó en aproximadamente 101 segundos frente a 161 segundos para DeepSeek-OCR-2.

El modelo completo es de código abierto.
